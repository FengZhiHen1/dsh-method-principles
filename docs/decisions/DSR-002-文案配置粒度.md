# DSR-002：文案配置粒度——单个 `text` 字段，消融以整段为单位

## 一行式速览

- **决定**：文案做成 `Config.text` 单字段，默认值为精简版文案；整段置空即完成一次消融。
- **理由**：满足"改文案不发版"，且消融实验的可观察单位是整段效果，逐条开关收益低于其配置面与实现复杂度。
- **被否决项**：文案硬编码（改字即发版）；逐条独立字段/开关（过度设计，消融粒度错配）。

## 上下文

附图第 3 条（消融实验）要求"某条规则、工具或提示词到底有没有用，可以在其他条件尽量不变时，删掉它再跑一遍对比"。这既是插件要传达的原则，也直接提出一个问题：插件自身要不要提供逐条原则的开关，以便做消融？

另一方面，文案大概率需要演进（措辞、条数、语言），改一次就发版重装的成本不低。

## 真实方向与评价

| 方向 | 配置面 | 改文案成本 | 消融粒度 | 评价 |
|---|---|---|---|---|
| A. `Config.text` 单字段 + 默认文案 | 1 个字符串字段 | 改 profile patch 一行，不发版 | 整段 | 覆盖两种真实需求 |
| B. 文案硬编码 | 无 | 每次改文案发版重装 | 无 | 配置面为零，但迭代成本高 |
| C. 逐条独立字段/开关 | N 个字段 | 逐条改，不发版 | 逐条 | 消融粒度更细，但配置面与实现复杂度最高 |

评价维度：配置与认知成本、改文案成本、消融粒度、实现复杂度。消融实验的可观察单位是"整段在 / 不在"——单条原则的效果在单次任务里信噪比极低，逐条开关的收益不成立；而"改文案不发版"是真实需求（措辞演进不可避免）。C 的额外配置面（空行处理、逐条拼接、缺省语义）与其收益不成比例。

## 最终决定

采用方向 A：`Config.text` 单字段，Schemastery schema 给默认值；`text: ''` 表示关闭该段。

## 直接后果

- 用户覆盖 config 时只写 `text`；其余键由 schema 默认值补齐。
- 消融实验以"该段在 / 不在"两组对照进行；逐条消融需手工改文案（可接受）。
- 默认文案成为包内常量，随包版本演进；用户覆盖后不随包升级变化。

波及文档：`../需求.md`（R-07/R-08、AC-07/AC-08）、`../项目结构设计.md`（配置形态）、`../technical-details/提示词段机制.md`（配置解析）。

## 重访条件

- 出现"只想关掉某一条、其余保留"的真实需求，且手工改文案不可接受时。
- 默认文案长度增长到需要按场景分组（如编码 / 评审 / 规划各一组）时。
