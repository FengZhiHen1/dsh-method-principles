# dsh-method-principles 需求

## 权威范围

本文唯一拥有本插件的目标、用户、场景、功能需求、约束、非目标与验收条件。技术选型与版本基线归 `技术栈设计.md`，模块与目录事实归 `项目结构设计.md`，机制与失败语义归 `technical-details/`，部署步骤归 `technical-details/部署.md`，选型理由归 `decisions/`。本文不定义机制、模块、目录或部署步骤。

## 结论先行

- 目标：把一小组方法论原则作为独立系统提示词段常驻注入 DSH，对全部 agent（含子代理）生效，用来约束"如何判断做得对不对"，而不是重复 DSH 已内化的通识流程。
- 已确认结论：默认文案取自洽精简版（附图 8 条各 1–2 行，英文，第 1 条含"先说明成功标准"，逐字内容见 `technical-details/提示词段机制.md`）；配置面取 `Config.text` 单字段加精简默认值；生效范围为全局段；交付形态为薄壳插件。理由见 `decisions/` 三份记录。
- 阅读重点：先读范围与约束，再读验收条件；实现精度要求见 `technical-details/提示词段机制.md`。

## 背景与问题

DSH 的系统提示词由各插件按 order 注册的段落装配而成，内容集中在"工具怎么用"与"平台是什么"；它不承载"用什么方法判断结论是否成立"这一层。用户希望把附图（B 站 Build in Public 分享）蒸馏的 8 条方法论原则常驻进提示词。

该需求的自身约束来自附图论点：模型训练已内化大量通用知识与标准流程，提示词的价值在于**几行能调动已有能力的提炼**，而非上千行说明。因此本需求的成功标准是"以最小常驻成本换到可观察的方法论约束"，不是"把 8 条原理写全"。

## 用户与场景

- 主要用户：本机 DSH 用户。
- 场景一（会话装配）：任意会话、任意 preset 的 agent 在装配系统提示词时都带上该段，无需用户每次交代。
- 场景二（文案演进）：用户调整文案时只改 profile patch 层的一行 config，不需要改插件代码或重新发版。
- 场景三（消融实验）：用户用"该段在 / 不在"两组对照跑同一任务，判断这 8 条是否真的改变行为。
- 场景四（显式关闭）：用户认为该段无价值时，把 config 文本置空即让该段从提示词中消失。

## 约束

- C-01 不改变 DSH 原生段：不得修改、遮蔽或重排 `harness:identity`、`deployment:persona`、各工具段等既有段。
- C-02 不引入运行时服务：插件不提供 Service、不注册工具、不注册动态上下文、不注册提示词变量。
- C-03 段名全局唯一：同一 layer 内重名会导致挂载失败；跨 scope 重名会被遮蔽而非合并。
- C-04 文案不得包含 `{{...}}` 变量引用：未注册变量会使该 scope 的装配失败。
- C-05 文案为纯静态文本：不得依赖装配上下文（无按 scope 变化的内容）。
- C-06 唯一持久副作用是段注册；不写文件、不访问网络、不持久化状态。
- C-07 运行环境为 Node `^22.19.0 || >=24`；包为 ESM。
- C-08 插件自足：默认文案不依赖任何工作区的 `AGENTS.md` 或 skill 是否在场。
- C-09 发布前必须过试验环境实测门禁；稳定环境只吃发布物，禁止源码直挂。
- C-10 不得未经用户明确指令重启或关闭任何运行中的 DSH 实例。

## 非目标

- 不新增工具、不新增 UI、不新增设置页入口（不做客户端半侧）。
- 不做逐条原则的独立开关或独立字段（消融以整段为单位）。
- 不承诺提示词段一定能改变模型行为；该假设由消融实验检验，不作为需求成立的前提。
- 不做多语言切换、不做文案模板变量、不做文案版本管理。
- 不修改 `AGENTS.md`、不改动 `knowledge/`、不发布 npm 包（发布路径未到时机）。
- 不覆盖 `ptc`/`minimal`/`cordis` preset 的既有段语义，也不为其定制文案。

## 验收条件

- AC-01 组合验证：profile 的 `--dump-config` 中恰有一行 `id: method-principles` / `name: dsh-method-principles`，解析来源为该包。
- AC-02 段注册：装配结果中恰有一个 `name === 'deployment:method-principles'` 的段，且其 `order === 200`。
- AC-03 装配顺序：装配结果中该段的下标大于 `deployment:persona` 的下标、小于 `plan:policy` 的下标。
- AC-04 全局生效：Web UI 的系统提示词折叠行展开后可见该段；子代理会话同样可见。
- AC-05 不干扰原生段：装配结果中不存在 `complete` 段；`deployment:persona` 段内容与未挂载插件时逐字一致。
- AC-06 默认文案：不传 config 时，段文本等于默认文案常量（逐字断言）。
- AC-07 配置覆盖与关闭：`text: 'X'` 时段文本为 `X`；`text: ''` 时装配结果中不存在该段。
- AC-08 配置校验：非法 config（如 `text` 传入非字符串）导致挂载失败并给出可定位的校验错误。
- AC-09 生命周期：卸载后段消失、无残留；重新挂载后重新出现，且不产生重复段。
- AC-10 分层门禁：`node tools/plugin-layering-check.mjs plugins/dsh-method-principles` 通过（薄壳豁免）。
- AC-11 测试：`npm test` 全绿，覆盖 R-02/R-06/R-07/R-08/R-09 的正反用例。
- AC-12 部署门禁：试验环境 `--dump-config` 复查通过、启动无 `N entries did not activate`、系统提示词冒烟通过；稳定环境依赖为发布物形态，无源码路径残留。

## 假设

- DSH 系统提示词的段注册契约与中央 order 表在 `0.1.2-rc.1` 基线上保持稳定。
- `deployment:method-principles` 段名在用户的插件集合中保持唯一。
