# 部署

## 权威范围

本文唯一拥有本插件的包形态、部署通道、实测门禁、验证方法与失败排查。需求与验收条件归 `../需求.md`，段机制归 `提示词段机制.md`，选型与版本基线归 `../技术栈设计.md`。本文不定义机制内容。

## 结论先行

- 两个通道：实例 `test` 用 `link:` 源码直挂（实测门禁），实例 `stable-dev` 的 `web` profile 用 `github:` git 依赖（发布物形态）。
- 生效条件：bundle 成员变化**必须重启实例**；web 的重启由用户在 GUI 执行，本插件不自行重启任何实例。
- 实测门禁未通过前不得挂 web。
- **基线兼容性（2026-09-27 实测）**：本插件段契约两代等价，`0.1.2-rc.1` 与 `0.1.7-rc.2` 两个真实运行时各跑一次真实装配均为 28 行、下标 2、路由正确。差异仅在 persona 锚点形态（拆分），不影响插件行为——故**稳定实例无需为迁移插件而紧急升级**（升级仍按用户节奏）。

## 包形态

```text
dsh-method-principles/
├── package.json       # dsh.bundle.patch = "./cordis.patch.yml"
├── cordis.patch.yml   # - insert: [{ id: method-principles, name: dsh-method-principles }]
├── index.js           # 插件面（name / inject / Config / apply）
└── src/adapter/host.js
```

- `dsh.bundle.patch` 指向包内 patch；行 `name` 用包名，禁止源码相对/绝对路径（web 红线）。
- 包进 `dsh.profile.bundles` 即激活其 patch；安装到 `dependencies` 只是可解析，不等于激活。

## 部署通道

以下命令中的 HOME 与 bin 路径是示意值，每次部署动作前必须用 `dshl env --json` 重新取值（`instances[].home`、`instances[].version_bin`），不得照抄。

### 通道 A：test 实例（实测门禁）

```powershell
# 0. 取当日事实（每次部署动作前）——禁止凭记忆写版本号
node tools/dsh-launcher-cli/cli.mjs env --json

# 1. 源码直挂（HOME 与 bin 均取自上面的 env 输出）
$env:DSH_HOME='<test 实例 home>'
node '<test 实例 version_bin>' plugin --profile test add link:E:\Project\DSH_Plugins\plugins\dsh-method-principles

# 2. 组合复查（不启动）
node '<test 实例 version_bin>' --profile test --dump-config

# 3. 启动实测（由用户经启动器执行；agent 不自行起实例）
```

- 报 `ERR_PNPM_UNEXPECTED_STORE` 时追加 `--store-dir=<本机既有 store>`。
- `link:` 直挂会把插件自身 `node_modules` 的依赖一并投影进 profile；本插件仅依赖 Schemastery，投影面无核心服务包。

### 通道 B：web profile（发布物）

```powershell
$env:DSH_HOME='<stable-dev 实例 home>'
node '<stable-dev 实例 version_bin>' plugin --profile web add github:FengZhiHen1/dsh-method-principles#<ref>
```

- 前置条件：子仓库已 commit/push，顶层已提交 gitlink 更新，通道 A 实测通过。
- 首次 `add` 若被 pnpm 拦截 git 依赖的 `prepare`，按 pnpm 提示把包键写入该 profile 的 `pnpm-workspace.yaml` 的 `allowBuilds` 后重试。
- 装完后由**用户在 GUI 重启实例**，插件才生效。

## 验证方法

| 层次 | 方法 | 判据 |
|---|---|---|
| 包内 | `npm test` | 单元 + 生命周期 + 组合 + **真实运行时装配门禁**全绿（后者在无 DSH 运行时的环境下 skip） |
| 组合树 | `--dump-config` | 恰一行、来源正确、无重复（人工按层级核对——本代无重复 id 机械闸门） |
| 装配结果 | Web UI 系统提示词折叠行（`SystemPromptRow`），或 `verify/overlay-verify.mjs` 的装配报告 | 段可见且文本逐字一致；位置判据见 AC-03（persona 锚点见下） |
| 子代理 | 在会话中派发一个子代理，展开其系统提示词 | 同样包含该段（且仅基础块） |
| 卸载 | 移除插件行后重启（或 test 实例 `remove`） | 段消失、无残留 |

`--dump-config` 只证明组合树，不证明装配结果；装配结果以 Web UI 的系统提示词折叠行或 `verify/overlay-verify.mjs` 的装配报告为准。

⚠️ **persona 锚点随基线而变**：`verify/overlay-verify.mjs` 的装配报告新增 `personaAnchor` / `personaSuffixIndex` 两列——旧基线报 `personaAnchor=deployment:persona`，新基线报 `deployment:persona-prefix`。核对位置时先看这两列，再判 `afterPersona`/`beforePlan`（否则在新基线上会把"锚点不存在"误读成"位置不对"）。

## 失败排查

| 现象 | 原因 | 处置 |
|---|---|---|
| `N entries did not activate` 含 `method-principles` | `systemPrompt` 或 `agentPresets` 服务缺失（该 profile 未装载对应 bundle） | 补齐基础 bundle 后重启。⚠️ v0.1.7 起该条是**非致命 stderr 警告**（行详情格式 `id (name): …`，新增 `pending (waiting for services: X)`）；其致命兄弟是 `startup failed: N required plugin[s] did not activate` |
| `invalid config: … (at text)` | config 传了非字符串 | 修正 config |
| `prompt section "deployment:method-principles" is already registered` | 同一 profile 重复挂载本插件 | 只保留一处 |
| 同一 `method-principles` 行被 insert 两次 | bundle 层与用户 patch 层重复 insert 同一 id | **不会报错**——旧基线的 `duplicate loader entry id` 守卫**已被上游 revert 删除**（`dsh-v0.1.7-rc.2` 起），现为**后者静默胜出**，`--dump-config` 也不做重复 id 判别，只能人工核对各层行清单 |
| 行被自动禁用（`dsh: disabling profile plugin …`） | peer 版本不兼容门禁（v0.1.7 新增） | 本插件**无 `peerDependencies` 键**，不触发该门禁（`plugin-compatibility.ts:68` 直接返回 undefined） |
| 装配失败：`unknown prompt variable` | 自定义文案含 `{{...}}` | 移除变量引用 |
| UI 里看不到该段 | 实例未重启（bundle 成员变化未生效）或段被同名段遮蔽 | 重启实例；检查是否有其他段使用同名 |
| 段的位置断言报 `personaIndex=-1` / `n/a` | 顺序探针锚在旧代 persona 段名 `deployment:persona`，而 v0.1.7 已拆为 `-prefix`/`-suffix` | 探针已改为两代自适应（`verify/overlay-verify.mjs` 同时报告 `personaAnchor`） |

## 已知限制

- bundle 成员变化必须重启实例，热重载不覆盖该变化。
- 本阶段不发布 npm；`github:` 依赖未钉 ref 时由 lockfile 承载 commit，可接受但建议钉 ref。
- 本插件不自行重启任何运行中的实例；web 生效由用户在 GUI 完成。
